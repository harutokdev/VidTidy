# よく似ている動画の判定：精度の測定と改善（2026-10-02）

ユーザーと合意した順番（1. 測る仕組み → 2. 情報の少ない場面を証拠に使わない）の最初の2段階。測定は生成した動画だけで行い、ユーザーの動画は使わない。

## 1. 測る仕組み（tools/SimilarityBench）

```
dotnet run --project tools\SimilarityBench -- <作業フォルダー> runtime\ffmpeg\ffmpeg.exe runtime\ffmpeg\ffprobe.exe
```

- 5種類の動画（mandelbrot・testsrc2・life・cellauto・gradients、各20秒）を作り、人がよくする8通りの変え方（画質を落とした作り直し、縮小、拡大、明るさ、黒い帯、周りを切る、最初を0.3秒切る、最初を3秒切る）で40組の「似ている」組を作る。
- 「別の」組は、5種類どうしの10組と、ほとんど黒い別々の動画どうしの3組（暗い画面を小さな物が動く）。
- アプリと同じ5か所（長さの5%・25%・50%・75%・95%）から 9x8 の白黒フレームを取り、今の判定と新しい判定で全組を判定し、`report.md` に書く。

## 2. 情報の少ない場面を証拠に使わない

- 両方の動画で「真っ黒・一色・暗い画面に小さな物だけ」の場面は、似ているとも違うとも数えない。
- 指紋（64ビットの dHash）だけでは、黒い画面と、空のようななめらかなグラデーションを区別できない（どちらもビットがほぼ立たない）。指紋だけで判断すると gradients の7組を見落としたため、採用しなかった。
- そこで、指紋の線がほとんどない場面（立っているビットが8以下か56以上）に限って、保存済みの小さなフレーム画像（キャッシュ）を読み、9x8 の明るさの幅が32未満なら「平ら」とする。元の動画は読まない。
- 残った場面が3つ未満なら「似ている」としない。残りが5つなら従来どおり（4つ一致・3つ連続）、4つなら3つ一致・3つ連続、3つならすべて一致。

### 測定で見えた次の課題

- 黒い帯（3/5見落とし）・周りを切る（3/5見落とし）：黒い帯を切り落としてから指紋を作る、中央部分の指紋を併せて使う、で改善が見込める（合意済みの次の段階）。
- 最初を3秒切った（すべて見落とし）：長さで位置を決めているため。数秒おきの場面でずれを探す方式が必要（合意済みの次の段階）。
- cellauto の作り直し（画質を落とした）：細かい模様が圧縮で崩れる。2つ目の指紋（DCT 方式）で確かめる案。

## 4. 2つ目の指紋の比較：PDQ と pHash（測定のみ、採用しない）

- PDQ（Meta、BSD）を C# に移植した（`tools/SimilarityBench/PdqHash.cs`）。公式のテスト画像4枚（ThreatExchange `pdq/data/reg-test-input/dih/bridge-*.jpg`、参照実装と同じく 512x512 に最近傍で縮小）で、公式の値とビット単位で一致した（違い0ビット）。
- 比べ方：黒い帯を切った 256x144 の白黒フレームから PDQ を作り、1場面の上限は公式の画像向けの 31ビット、平均と最大は今の規則（64ビット中 8/6/12）と同じ割合（23/46）。画質スコアが両方50未満の場面は数えない。

## 5. アプリへの組み込み：黒い帯を切った指紋（bars-center-v1）

- 指紋の材料：動画は読み直さない。近似重複用に保存済みの場面画像（横1024まで）5枚を、FFmpeg 1回で 96x54 の白黒にして読む（`FfmpegAdapter.ReadStoredFramesGrayAsync`）。5枚を縦に積んで1枚として読む（concat フィルターは1枚ずつの画像入力だとフレームを落とすため使わない）。
- 計算：`NearDuplicatePreparation`（Core）。5枚すべてに出ている黒い帯を切り、全体・中央90%・中央80%の dHash と「平ら」かどうかを作る。測定の道具は同じ関数で測っており、道具の計算と一致することを毎回確かめる。
- 保存：`near_duplicate_preparation`（動画ごと、帯の幅と元にした場面の版）、`near_duplicate_prepared_frame`、`near_duplicate_prepared_lsh_bucket`。版番号付きの移行の外に置き、外部キーも付けない。古い版のアプリに戻しても、そのまま開ける。場面を取り直すと（updated_at が変わると）古くなり、作り直す。保存画像が読めない動画は「Unavailable」として、場面を取り直すまで今の比べ方だけを使う。
- 候補：今の候補に加えて、帯を切った指紋の帯（LSH）が同じ組。全体どうし、または片方の中央ともう片方の全体。長さ3%以内・完全一致を除く、は今と同じ。
- 判定：今の規則で「似ている」ならそのまま。そうでなければ、帯を切った指紋で同じ規則（HighPrecisionV1）を当て、通れば「似ている」。測定では似ている45組中38組（今は28組）、別の93組で間違いは0組。
- 進め方：走査の終わりに、まだ作っていない動画ごとに「作るだけ」のジョブを積む。1回の判定ごとに16本ずつまとめて作るので、ほとんどのジョブはすぐ終わる。新しく取った場面は、その場で作る。
- まだしていないこと：すでに判定済みの組（「似ていない」と出たものを含む）は判定し直さない。版（ThresholdVersion）は変えていない。判定し直しは、「このまま残す」を保つ移行と一緒に、後の段階で行う。

## 6. 長さが違う動画（測定段階、アプリにはまだ入れていない）

`SimilarityBench <作業フォルダー> <ffmpeg> <ffprobe> length` で測る。見本は、別々の場面8つ（約55秒）または60（約7分半）をつないだ生成動画。場面の切り替わりがある方が実際の動画に近い。

- `TimelineMatching`（Core）：動画全体から一定間隔で取った場面（黒い帯を切った指紋）を集合として比べ、両方で時刻の順番がそろう一致だけを数える（最長共通部分列）。短い方の場面の8割以上が長い方にあり、4枚以上一致すれば「含まれる」。始まりだけ同じ別の動画（シリーズの別の回）や、同じ場面のくり返しは通らない。
- `TimelineAlignment`（Core）：粗い一致で分かるのは、だいたいのずれだけ（場面の時刻がそろわないため）。同じずれの一致ごとに、両方の動画の20秒ほどを連続して読み（短い方は毎秒5枚、長い方は毎秒10枚）、最も多くの場面がそろうずれを0.1秒単位で決める。そのずれで、短い方の全場面を長い方のちょうどの時刻と1対1で比べ直す。途中を削った版は、ずれが2つに分かれる。長い所は、ずれでつながる範囲の外側として出す。短い方の最初と最後もずれで重ねるので、間隔より短い切り落としも出せる。
- キーフレームに合わせる取り方も試したが、生成した動画（スマホの動画も）はキーフレームが一定間隔で場面の切り替わりにないため、正確な時刻より劣った（27/40）。採用しない。

| 取り方 | 含まれる49組で見つけた数 | うち長い所が合っていた数 | 別の31組で間違えた数 | 1本の場面数（平均） |
|---|---:|---:|---:|---:|
| 2秒おき（補正なし） | 36 | 18 | 0 | 66.8 |
| 5秒おき（補正なし） | 40 | 33 | 0 | 26.8 |
| 2秒おき＋ずれ補正 | 46 | 40 | 0 | 66.8 |
| 5秒おき＋ずれ補正 | 49 | 49 | 0 | 26.8 |
| 10秒おき＋ずれ補正 | 35 | 34 | 0 | 13.5 |
| 20秒おき＋ずれ補正 | 6 | 6 | 0 | 6.7 |

- 10秒おきは、約7分半の長い動画では9組すべて見つけた。落としたのは約55秒の短い動画（場面が5枚しかない）。20秒おきは長い動画でも9組中6組。
- 2秒おきが5秒おきより劣るのは、1コマごとに絵が丸ごと変わる生成場面（cellauto など）で、0.1秒刻みのずれでもそろわない場面が増えるため。実際の映像ではまれ。
- 費用の目安：1080p の生成動画で、24枚ずつまとめて読むと1枚約0.04秒（SSD）。実際の動画はキーフレームの間隔が長く HDD のシークも加わるので、1枚0.1〜0.3秒と見込む。連続して読む20〜30秒の区間は0.4秒ほど。

## 7. アプリへの組み込み：長さが違う動画（timeline-5s-360-v1）

- 取り方（A 案、2026-10-03 にユーザーと決定）：30分までは5秒おき、それより長い動画は1本360枚まで（1時間なら10秒おき）。20秒未満の動画には作らない（`TimelineSamplingPolicy`）。
- シークを減らす工夫：最初の20秒分のパケットだけを読んでキーフレームの間隔を調べ、1枚ずつ取ると動画1本分より多く読む（キーフレームの間隔の半分＋1秒 ≥ 取る間隔）ときは、頭から順に1回だけ読む（10分ずつ区切って続けて読む）。それ以外は24枚ずつまとめてシークして読む。順に読むときは `fps=…:round=up` を使う（既定の丸めだと半間隔早い場面になる。測って確認）。
- 場面の時系列は、動画を読む保護付きの処理（ProtectedSourceOrchestration の NearDuplicateFingerprint 段階）の中で作り、公開が成功してから保存する。元の動画が変わっていれば保存しない。解析済みの動画は、走査の終わりに時系列のない動画として同じ処理に積む。
- 候補：時系列の指紋の帯が2枚以上の場面で共通し、長さが3%より違い、中身が完全一致でない組。64本より多くの動画に共通する帯（黒い場面やロゴ）は使わない。黒い場面は帯に入れない。
- 判定：保存した時系列どうしで粗く比べ、1枚でも一致すれば、両方の動画に保護をかけてから `TimelineAlignment` で細かく比べる（ずれを測る20秒ほどの区間と、短い方の全場面に対応する長い方の場面だけを読む）。結果は近似重複の証拠（ThresholdVersion `timeline-contained-v1`）として残し、「含まれる」なら長い所も残す。各組は、2本目の時系列ができたときに1回だけ判定する。
- 画面：組の注意書きに「B の方が長く、最初の 0:03 と 20:00〜30:00 が A にはありません。」と出す。
- 測定（変更後に取り直し）：5秒おき＋ずれ補正で含まれる49組中48組、2秒おきで49組すべて。別の31組の誤判定は0組のまま。
- 表は版番号付きの移行の外に置き、外部キーを付けない（古い版でも開ける）。

## 8. 判定済みの組の判定し直し（2026-10-07）

- 対象：黒い帯を切る前の版で「似ていない」（Rejected / InsufficientEvidence）と判定された組。両方の動画に帯を切った指紋（`near-duplicate-preparation`）ができたら、その指紋で同じ規則（HighPrecisionV1）をもう一度当てる。動画は読まず、保存済みの指紋だけを使う。
- 「似ている」になったときだけ、同じ組・同じ版の証拠を更新する（証拠の ID とグループの ID は組と版で決まるので変わらない）。「似ている」と判定済みの組には触れないので、グループと「このまま残す」などの判断はそのまま残る。版（ThresholdVersion）は変えない。
- 判定し直しは帯を切る版ごとに1回だけ。済んだ組は `near_duplicate_recheck`（証拠 ID と帯を切る版）に記録する。表は版番号付きの移行の外に置き、外部キーを付けない。
- いつ行うか：走査の終わりに、専用の処理（`MediaPipeline.RecheckRejectedNearDuplicatesAsync`）で行う。対象は「似ていない」のまま今の版で判定し直していない組のうち、両方の動画が今もあり（中身も同じ）、両方に今の版の帯切りが済んでいる（作れた、または保存画像が読めないと分かった）組だけ。こうして並べた組は、結果が「似ている」になっても「似ていない」のままでも必ず記録するので、一覧は毎回減って空になる。通常の判定の流れは今までどおり（判定済みの組は飛ばす）。
- 記録は、格上げの保存が済んでから書く。保存に失敗したら記録せず、次の走査でもう一度判定する。
- テスト：`NearDuplicateRecheckTests`（帯切りの後に判定し直して組になる／帯切りが済んだライブラリでも次の走査で判定し直す／似ていないままの組は記録されて繰り返さない／済んだ組は判定し直さない／似ている組には触れず、グループと「このまま残す」が残る）。判定し直しを止めると前の3つが失敗することを確かめた。
- 測定の注意：FFmpeg の `gradients` は seed を指定しても色と位置を乱数で決めるため、生成動画が毎回変わる。`NearDuplicateTimelineTests` は色と位置を指定して固定した（以前は約4回に1回失敗していた）。`tools/SimilarityBench` は今も乱数のまま。
